# Plan 05-01: Secure local WebUI and task API

## Task 1: Web server trust boundary

Create a stdlib HTTP server with fixed routes for the dashboard, status,
task creation/status/cancellation and static assets. Enforce bounded HTTP
parsing, Host/Origin/session/CSRF/CSP rules and loopback-default/non-loopback
TLS+token startup policy. Keep all task dispatch through `MercuryApplication`.

Verification: loopback client tests cover normal page/API operation plus bad
Host, foreign Origin, missing CSRF/session, oversized body, invalid content
type and non-loopback TLS/token rejection before a socket listener starts.

## Task 2: Accessible static dashboard

Add semantic HTML/CSS/native JavaScript, a live task progress view, evidence
table, status capability panel and bounded forms for existing diagnose,
paired, discover and trace request shapes. The client may poll/cancel through
the API but may not directly probe.

Verification: static-resource tests assert CSP-compatible external JS/CSS,
labels, landmarks, status text and no inline event handlers; API tests prove
the submitted request reaches the same application facade result.

## Task 3: CLI lifecycle

Expose `mercury web` only as a small lifecycle adapter around the web server,
with explicit bind/cert/key/token options and stable shutdown behavior.

Verification: parser tests reject arbitrary endpoint/protocol knobs and a
controlled loopback startup/shutdown smoke passes.
