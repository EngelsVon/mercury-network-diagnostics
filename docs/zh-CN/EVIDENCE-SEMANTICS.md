# 证据语义

[English](../EVIDENCE-SEMANTICS.md) · [README](../../README.zh-CN.md) · [架构](ARCHITECTURE.md)

## 概览

Mercury 报告观测、能力、结论和任务状态，而不是把网络行为压缩为单一的“可达/不可达”布尔值。模型架构带有版本（本版本为 `1.1`），兼容的历史文档保留其架构定义的含义。

本指南是 CLI 输出、WebUI 行、JSON、历史比较与报告的解释契约。

## 观测契约

一条 `Observation` 包含：

| 字段 | 含义 |
| --- | --- |
| `evidence_kind` | 实际观测到的协议或执行事实 |
| `disposition` | 语义类别：肯定、否定、不确定、不可用、错误或已取消 |
| `direction` | 本地、出站、入站或反向 |
| `target` | 选定端点或本地观测对象 |
| `started_at`、`ended_at`、`duration_ms` | 有时间边界的测量语境 |
| `attempt` | 逻辑尝试编号 |
| `source` | 来源，例如 Mercury 适配器、对端回执或原生工具 |
| `detail` | 有界、证据特定的结构化元数据 |

每种证据只允许兼容的处置。例如，`tcp_connected` 为肯定，`tcp_refused` 为否定，`timeout` 为不确定，`permission_denied` 为不可用。该校验防止渲染器把静默重新标为连接成功或失败。

## 核心处置

| 处置 | 解释 | 示例 | 不能证明什么 |
| --- | --- | --- | --- |
| `positive` | 观测到定义明确的响应、本地事实、对端到达或确认 | TCP 已连接、DNS 应答、HTTP 响应、原生 ping 回复、对端回执 | 超出精确配置文件、方向、端点和时间窗口的普遍可达性 |
| `negative` | 观测到选定协议的直接否定响应或已验证的协议失败 | TCP 拒绝/重置、网络/主机/ICMP 不可达、管理禁止、TLS 验证失败 | 所有其他承载通道或路径均不存在 |
| `inconclusive` | 尝试结束，但证据无法区分可达、过滤、丢包、延迟或静默 | 超时、UDP 静默、路由跃点未应答 | 成功、失败、端口关闭或隔离有效 |
| `unavailable` | 无法使用该能力 | 平台/工具不支持、缺少权限 | 否定可达性 |
| `error` | Mercury 或有界适配器无法生成有效协议证据 | 执行错误、解析失败、未分类原生失败 | 网络结论 |
| `cancelled` | 操作员或生命周期停止了已接纳任务 | 任务/尝试已取消 | 未执行尝试的结果 |

## 各协议解释

### DNS

`dns_answer` 是针对已记录应答与查询语境的肯定证据。`dns_failure` 根据具体解析器结果可以是否定、不确定或错误。主动主机名任务根据私有解析快照规划，并在连接前复核；如果应答变为公网或逃逸声明范围，任务会被策略拒绝，而不会连接到新地址。

双端 `dns_udp` 与 `dns_tcp` 配置文件和已配置 Mercury 接收端交换固定、关联绑定的 DNS 消息，不提供任意递归解析。

### TCP

- `tcp_connected`：选定 TCP 连接完成。
- `tcp_refused`：目标对该端点和尝试返回拒绝。
- `tcp_reset`：观测到重置。
- `network_unreachable` 或 `host_unreachable`：收到直接不可达状态。
- `timeout`：在记录窗口内未获得确定 TCP 结果。

拒绝是针对被测 TCP 端点的直接否定证据。超时不等于拒绝，也不能证明防火墙阻止了连接。

### UDP

`udp_application_reply` 或关联绑定的对端回执，是精确固定交换的肯定证据。`icmp_unreachable` 是与所尝试数据报关联的直接否定证据。`silent` 和 `timeout` 仍属不确定，因为 UDP 无须回复，且返回路径证据可能被过滤或丢失。

### TLS、HTTP 与 SSH banner

`tls_handshake` 记录已完成、经验证的配置握手。`tls_verification_failed` 和 `tls_handshake_failed` 保留各自的具体失败语义，不会重写为通用 TCP 失败。`http_response` 记录 HTTP 层响应；其处置取决于具体协议证据。`ssh_banner` 只记录已配置的 banner 交换。Mercury 不尝试密码、凭据或登录。

### ICMP 与路由证据

`native_ping_reply` 是肯定的原生 echo 证据。超时仍是不确定，权限拒绝是不可用，未分类的非零原生退出则保留为失败/错误证据，而不会猜测为某种 ICMP 含义。

`path_hop` 报告原生路由观测。`path_hop_unanswered` 与 `path_incomplete` 仍属不确定。路由跃点、网关或邻居记录不是接入交换机的直接证据。

### ARP、IPv6 ND 与 LLDP

ARP 和 IPv6 邻居发现是同链路事实。在双端评估中，本机与对端位于不同子网会使这些配置文件成为 `not_applicable`；该行不说明跨子网可达性。同链路邻居事实也不能证明应用可达性。

只有存在直接 LLDP 证据时，Mercury 才把基础设施识别为直接邻居。它不会从路由、网关、Wi-Fi、ARP 或 ND 观测推断交换机身份。

### 原生 Nmap

Nmap 派生的端口状态使用 `native_port_state` 和原生来源。Mercury 保留：

| 原生状态 | Mercury 处置 | 解释 |
| --- | --- | --- |
| `open` | 肯定 | Nmap 对选定固定配置文件报告端口开放 |
| `closed` | 否定 | Nmap 报告端口关闭 |
| `filtered` | 不确定 | Nmap 报告存在过滤，无法得到确定的开放/关闭状态 |
| `open|filtered` | 不确定 | Nmap 无法区分开放与过滤 |

这些是原生工具报告，并不是 Mercury 观测到等价直接套接字交换的声明。Nmap 缺失、权限不足、超时、XML 异常和适配器错误仍是不同结果。

## 覆盖矩阵语义

每个请求的双端覆盖配置文件按方向生成矩阵行。每行携带配置文件、方向、适用时的已配置端口、结果、支持证据种类、来源、时间与限制。

| 覆盖结果 | 含义 |
| --- | --- |
| `candidate_carrier` | 精确选定交换存在肯定证据；它可能在被测边界上传递数据 |
| `direct_negative` | 选定配置文件产生了直接否定证据 |
| `inconclusive_silence_or_timeout` | 静默或超时阻止了结论形成 |
| `unsupported` | 所需能力不受支持 |
| `permission_denied` | 所需能力存在但未获权限 |
| `skipped` | 该配置文件/方向未产生适用的已执行结果 |
| `not_applicable` | 配置文件不适用于该拓扑，例如跨子网 ARP/ND |

`candidate_carrier` 有意比“发现隧道”更窄。它表示被测承载通道传递了定义明确的交换，或产生了另一种可接受的肯定信号。是否实际部署隧道需要其他证据。

所有非候选行都会作为缺口或有范围的否定结果保留。即使矩阵没有空行，它也只覆盖实际发出的配置文件、端口、报文形状、方向和时间窗口。Mercury 绝不会将其转换为“所有隧道均不存在”的普遍陈述。

## 方向与对端关联

方向属于证据本身，而不是表现层元数据：

- `local`：有关执行端点的事实。
- `outbound`：发起端点向已配置对端或目标发送。
- `inbound`：执行接收器观测到到达。
- `reverse`：已配置对端执行互逆方向。

`CoverageReceipt` 记录关联 ID、配置文件、源/目标元组、到达时间、SHA-256 载荷摘要、载荷长度、方向、来源和回复结果，但不保留原始测试标签。评估使用短期关联标识符关联发送端观测与回执；无关报文不会被接受为交换证明。

## 结论、置信度与健康状态

`Conclusion` 包含标题与摘要、健康状态、置信度、支持观测 ID、替代解释和限制。置信度描述引用观测对该范围内结论的支持强度，并不是整个网络健康的概率。

任务健康状态同样有范围。“健康”或“已完成”表示其定义的生命周期按照证据规则完成，不表示每个端点都可达。对于部分、失败、未知或取消的任务，必须结合其观测、能力、错误和终止原因解释。

## 能力证据

能力使用以下状态：

- `available`
- `unsupported`
- `permission_denied`
- `missing_tool`
- `error`

能力证据回答 Mercury 能否执行或补充某项测量，并非连通性证据。例如，缺少原生 ping 工具不表示目标未响应 ICMP，而表示 Mercury 无法通过选定适配器运行该测量。

## 时间、来源与计量

每条观测都有带时区的起止时间戳和非负耗时。来源标识适配器或对端证据源。只有任务种类和模型架构兼容时才应比较证据，同时要考虑计划、时间窗口、能力状态和方向的差异。

预算字段使用逻辑计量单位：

- 尝试速率统计逻辑尝试启动数。
- 数据报和逻辑报文计数描述 Mercury 计划产生的任务量。
- 应用字节计数描述有界载荷数据。
- 事件和输出上限约束记录的生命周期数据。

这些不是抓包测量，不统计精确链路层开销、内核重传或每一个线上字节。

## 历史、比较与脱敏

历史记录请求与生效配置、不可变上限、证据、终止状态和安全生命周期数据。秘密材料在持久化前被拒绝。报告默认脱敏主机名、IP 地址、MAC 地址和载荷；即使操作员显式保留其他敏感标识符，凭据材料仍会被排除。

历史比较描述兼容记录证据之间的新增、移除和变化。某条观测在一次运行中缺失，表示“该次运行未记录”，并不会自动成为直接否定，也不能在缺少匹配协议证据时显示为已证实的退化或修复。

## 安全措辞指南

优先使用与证据绑定的表述：

| 推荐 | 避免 |
| --- | --- |
| “在记录时间，选定端点的 TCP 连接被拒绝。” | “主机已宕机。” |
| “超时前未收到 UDP 回复或关联回执。” | “UDP 被阻止。” |
| “对端记录到了出站方向的带标签 DNS/UDP 交换。” | “存在 DNS 隧道。” |
| “ARP 不适用于该跨子网端点对。” | “对端在二层不可达。” |
| “Nmap 以原生来源报告 `filtered`。” | “Mercury 证明防火墙丢弃了报文。” |
| “本次有限矩阵未记录候选承载通道；所列缺口仍然存在。” | “没有任何隧道能穿过该边界。” |

## 报告检查表

依据结果采取行动前，请确认：

1. 目标与授权范围和预期私有环境一致。
2. 配置文件、端口、报文形状、方向和时间窗口与问题一致。
3. 证据种类和处置支持所使用的措辞。
4. 能力缺口、超时、静默、取消和不适用仍然可见。
5. 来源能够区分 Mercury 直接证据、对端回执、本地事实和原生工具报告。
6. 结论包含合理的替代解释与限制。
7. 没有把有限结果呈现为针对所有路径、报文序列、协议或隧道的证明。
